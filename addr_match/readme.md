# Резервный матчер адресов

Локальный путь для HR-бота на случай, когда геокодер недоступен или вернул точность до города. На входе строка кандидата и город из разговора. На выходе до трёх `etalon_id` либо пустой список: отказ, бот переспрашивает.

Без LLM, без эмбеддингов, без GPU. Фонетическая нормализация, разбор номера дома, нечёткий поиск улицы по справочнику и логистическая модель отказа. В рантайме нужны только `rapidfuzz` и `numpy`.

## Результат

Все 500 размеченных строк, `python run.py --adresses adresses_labeled.jsonl --etalon etalon.jsonl`:

| top-1 | top-3 | точность отказов | полнота отказов | p50, мс | p95, мс |
|---|---|---|---|---|---|
| 0.9925 | 0.9975 | 0.9901 | 1.0 | ~1.9 | ~3.0 |

По каналам top-1: voice 0.9943 (348 из 350), webchat 0.98 (49 из 50). Все 100 негативов получили отказ, ложный отказ один.

Два из трёх промахов top-1 приходятся на дубли эталона: один и тот же адрес под двумя id, а разметка выбрала второй. Если считать дубль одним адресом, top-1 равен 399/400. Эти цифры посчитаны на данных, на которых я подбирал правила, поэтому они оптимистичны. Разбор, насколько именно, в разделе «Где ломается».

## Запуск

```bash
pip install -r requirements.txt
python run.py --adresses adresses_labeled.jsonl --etalon etalon.jsonl
python run.py --adresses adresses_labeled.jsonl --etalon etalon.jsonl --predictions preds.jsonl
```

Пути принимаются в обоих видах: `etalon.jsonl` и `data/etalon.jsonl`. Если файла нет по указанному пути, `run.py` ищет его в `data/`. На файле без меток (`sample_input.jsonl`) метрики качества печатаются как `null`, добавляется `n_rejected`.

Проверено в чистом venv на Python 3.12. scikit-learn нужен только `train.py`.

```bash
python train.py                # 5x5 CV, чувствительность к порогу, пишет models/model.json
python scripts/baseline.py     # наивный fuzzy без разбора строки
python scripts/ablation.py     # что даёт каждый шаг пайплайна
python scripts/stress.py       # порча поля city и сбой разбора дома
python scripts/selfcheck.py    # каждый из 1000 адресов эталона как запрос
python tests/test_parse.py     # регрессионные тесты на строках из данных (работает и через pytest)
```


## Что показали данные

До кода я прочитал все 500 размеченных строк. Почти каждое решение в пайплайне выросло из этих наблюдений.

**Шум voice системный, а не случайный.** «улеца краснозвиздная», «киравсгой», «ошорсгая», «никалойотрады», «атрес». Это оглушение согласных, редукция безударных гласных, «-ого» как «-ова». Если свернуть эти замены в один ключ, большинство искажений совпадает с эталоном точно или с одной правкой. Поэтому фонетический ключ, а не эмбеддинги: эмбеддинги кодируют смысл, а здесь нужна форма имени собственного.

**Номер дома несёт половину ответа.** 470 из 1000 адресов стоят на улицах, где в эталоне больше одного дома. Номер звучит словами («триста восемьдесят один к три»), корпус приходит как «к», «корпус», «карпус», «дробь», «тробь», буква как «бэ», «ка», «дэ». Разбор дома пришлось делать отдельным модулем.

**Поле city слабое.** У позитивов оно совпадает с городом ответа в 349 из 400 строк, пусто в 31 и в 20 указывает на другой город эталона. При этом 52 названия улиц есть в нескольких городах, Кирова и Мира в четырёх. Город годится только как признак, фильтровать по нему нельзя.

**Негативы отличаются улицей, а не городом.** Улиц из негативов нет в эталоне ни в одном городе, это сказано в условии, и я проверил: близких по написанию почти нет. Значит, отказ в первую очередь зависит от того, насколько хорошо нашлись улица и дом.

**В эталоне 5 дублей.** Одинаковые город, улица и дом под разными id: Магеллана 2, Калужское 22-й км 10 и 10П, Сергея Есенина 41, Ленинградский 311. У трёх пар координаты совпадают, у двух расходятся на 93 и 198 м. В разметке на дубли ссылаются 6 строк: в 4 выбран первый id, в 2 второй. Для метрики это монетка, для бота одна и та же точка.

## Пайплайн

**1. Токенизация** (`text.tokenize`). Нижний регистр, ё→е, пунктуация в пробел, цифры отрываются от букв («ленина54» → «ленина 54», «д67» → «д 67»), дефисы внутри слов режутся («30-летия»), сокращения вида «пр-т» и «б-р» сохраняются. Порядковое «2-я» после токенайзера склеивается обратно в «2я», одинаково в запросе и в эталоне. Иначе эталонное «6-й» теряло «й» как инициал, и запрос «6й» с ним не совпадал.

**2. Починка склеек и разрывов** (`QueryParser._repair`). Словарь строится из эталона, а не из разметки: слова названий улиц, типы улиц, числительные, слова-паразиты. Слово режется, только если его нет в словаре и оно не отстоит от слова улицы на одну правку. Разрез принимается, когда обе части известны или одна из них «сильная»: словарное слово от 4 символов, длинное числительное, тип улицы. Так «шоссемосковское» становится «шоссе московское», «пятьдесятдва» становится «пятьдесят два», «еслизнаете» становится «если знаете». Обратная операция склеивает разрывы, если вместе получается числительное, тип или паразит: «одинна дцать» становится «одиннадцать». Разрывы внутри названий («радиа льная», «гвардей ской») здесь не чинятся: их закрывает шаг 7, хотя и с пониженной уверенностью (P 0.88 и 0.95 на двух таких строках).

**3. Группа дома ищется с конца фразы.** Идём справа налево, пропуская паразиты («это самое», «так», «нахожусь»), пока токены похожи на часть номера: цифры, числительные, буквы, маркеры корпуса, «дом». Всё левее группы считается улицей. Направление важно: числа в названиях («9 Мая», «60 лет Образования СССР», «22-й км») стоят левее номера и с домом не путаются. Перед этим отрезается хвост про квартиру, подъезд или этаж, если перед ним уже было число: «ленина 28 кв 12». В размеченных данных таких строк нет, это страховка для живого трафика. Без неё «подъезд» нечётко распознавался как «пятьдесят». Два правила для улиц из цифр. Если внутри числовой группы стоит «дом», числа левее него уходят в улицу: «квартал сто десять дом один корпус два». Если на улицу не осталось ни слова, а в группе два числа цифрами, первое становится названием: «квартал 110 1к2». Оба случая нашла самопроверка по эталону, в разметке их нет.

**4. Номер дома собирается в канонику** (`numbers.py`). Числительные складываются по разрядам: «триста восемьдесят один» = 381. Если разряд уже занят, следующее число считается корпусом: «три один» = 3к1, «двадцать один пять» = 21к5. Так устроены голосовые ответы в данных. Буквы корпуса и короткие маркеры сравниваются по сырому тексту, а не по фонетическому ключу, потому что ключ склеивает «бэ» с «пэ» и «гэ» с «к». «ка» неоднозначна: это буква К («161ка») или корпус А («11кА»). Парсер отдаёт обе гипотезы, выбирает эталон. Нечёткое распознавание числительных (одна правка) включено только для слов от 5 символов, иначе «ясная 31» превращалась в дом 1к31.

**5. Остаток становится улицей.** Из него убираются паразиты, тип улицы и город, если его назвали в самой строке. Тип и город сохраняются как признаки. Город в строке ищется почти точно и не длиннее эталонного названия, иначе у «Красноярский рабочий» отрезалась бы половина. Разговорные формы («в нижнем», «екб») сравниваются по сырому тексту: по ключу «нижний» совпадает с «нижне» из «Нижне-Печерской».

**6. Фонетический ключ** (`text.key`). Удаляются ъ и ь, «-ого/-его» заменяется на «ова», «тс/дс» на «ц». Гласные сводятся: о, я → а; е, э, й, ы → и; ю → у. Звонкие оглушаются: б→п, в→ф, г→к, д→т, з→с, ж и щ → ш. Повторы схлопываются. После этого «пирфомайский» и «первомайский», «краснозвиздная» и «краснозвёздная», «киравсгой» и «кировской» дают одинаковые ключи. Поверх ключа срезаются хвостовые гласные, это грубый стем против падежных окончаний.

**7. Поиск улицы** (`Matcher.street_scores`). Берутся все подотрезки фразы длиной до 6 токенов. Каждый превращается в ключ без пробелов, поэтому склейка и разрыв дают одну и ту же строку. Одним вызовом `rapidfuzz.process.cdist` считается Левенштейн-ratio против всех 741 варианта названий. Варианты строятся из эталона: полное название, без званий («Героя Советского Союза», «Маршала», «Академика», «имени»), без инициалов. Дополнительно partial_ratio по ключу всей фразы ловит остаточные склейки, а coverage показывает, какую долю фразы объяснил лучший подотрезок. Дальше идут 25 лучших улиц.

**8. Кандидаты и скор.** Кандидаты это все дома этих 25 улиц. У каждого 15 признаков: совпадение улицы (ratio, partial, coverage, отставание от лучшей улицы запроса), тип улицы (совпал или конфликтует), дом (точное совпадение с учётом альтернатив, совпал основной номер, похожесть суффикса), город из поля и город из строки (совпал или конфликтует). Скор это линейная комбинация с ручными весами. Дубли эталона ставятся рядом, чтобы оба попали в top-3.

**9. Отказ.** Логистическая регрессия на 10 признаках запроса: скор лидера, отрыв от ближайшего кандидата, не считая дублей, совпадение улицы и coverage у лидера, совпадение дома, отсутствие дома, пустое поле города, число слов и число слов, которые улица не объяснила. Выход это P(top-1 верен). Порог выведен из цены ошибок, а не подобран. Если отправить человека не по адресу стоит как три переспроса, отвечать выгодно при P > 1 − 1/3 ≈ 0.667. Поверх модели одно ограничение: если первое место делят k разных адресов с одинаковым скором, P не выше 1/k. Так бывает, когда одна улица с тем же домом есть в двух городах, а города в запросе нет: «Лескова 21» есть в Новосибирске и Нижнем Новгороде. Ничьих в разметке нет, модель их не видела и уверенно выбирала один из двух городов. Теперь это отказ, и бот переспросит город. В `scores` у первого кандидата лежит эта вероятность, у следующих она же, умноженная на exp(s_i − s_1).

Почему такой порядок. Дом отделяется раньше улицы, потому что улица определяется как «всё, что не дом», а группа дома надёжно находится с конца. Фонетика применяется до нечёткого сравнения: voice-ошибки системные, и после свёртки расстояние падает до 0 или 1 правки. Город подключается последним и только как признак, потому что в 13% позитивов поле пустое или неверное.

## Почему без LLM

Справочник закрытый и маленький, 701 улица. Ошибки в строках фонетические и повторяющиеся. Правила плюс Левенштейн дают здесь 0.99 top-1 за 2 мс на одном ядре CPU. LLM добавила бы сотни миллисекунд, требования к железу и главный для этой задачи риск: уверенно сгенерированную улицу там, где правильный ответ «не знаю». Решение об отказе я бы не отдал генеративной модели без отдельной калибровки.

Решение не опирается на LLM API, поэтому пункт про локализацию не нужен. Если бы понадобилось, я бы взял малую открытую instruct-модель (Qwen2.5 1.5B или 3B в GGUF Q4 через llama.cpp, это порядка 1-2 ГБ памяти) только для переписывания строк из серой зоны в канонический вид, например «десять корпус комната 513». Матчинг и отказ остались бы текущими. Задержку такого варианта я не мерил.

## Что пробовал и отбросил

**Наивный fuzzy без разбора** (`scripts/baseline.py`): вся строка кандидата против «тип улица дом» из эталона. top-1: WRatio 0.33, token_set_ratio 0.69, partial_ratio 0.73. Номер дома и тип тонут в строке, числа словами не совпадают с цифрами, паразиты перевешивают короткие названия. После этого стало ясно, что строку надо разбирать на улицу и дом.

**Первая версия разбора дома** давала 373 точных номера из 400. Основные грабли: сравнение букв через фонетический ключ («бэ» → «п», «г» → «к»), нечёткие числительные на коротких словах («ясная» → «одна»), заминка «э» как буква, склейка «кдва». После исправлений 398 из 400: 396 напрямую и 2 через альтернативную гипотезу для «ка».

**Обученные веса ранжирования.** Логистическая регрессия на кандидатах (class_weight=balanced) на 5x5 CV дала top-1 0.9905 против 0.9925 у ручных весов и точность отказов 0.982 против 0.990. Разница меньше строки на фолд, но в пользу ручных, и ручные читаются. Для обучаемого ранжирования здесь мало трудных примеров: модель учится на трёх-четырёх строках.

**Отказ по одному скору лидера.** CV: top-1 0.9915, точность отказов 0.986, полнота 0.996. Модель на 10 признаках на CV не пропускает ни одного негатива.

**Признак «город из поля не из эталона».** Кажется очевидным, что чужой город означает негатив. На CV прирост ноль: все негативы и так отказываются по улице. А в стресс-тесте, где у позитивов поле города заменено на город вне справочника (Саранск), признак резал верные ответы: top-1 0.975 вместо 0.9925, 8 ложных отказов вместо одного. Условие прямо говорит, что поле бывает кривым, поэтому признак убран. После этого все четыре режима порчи поля (как есть, пусто, чужой город эталона, город вне эталона) дают одинаковые метрики.

**Стемминг.** Абляция эффекта не показала, 0.9925 с ним и без. Оставил, потому что он страхует падежные окончания («на санаторной» против «Санаторная»), ничего не стоит по задержке и на этих данных ничего не ломает.

Абляции (`scripts/ablation.py`). top-1 и top-3 считаются без отказа, то есть это чистое ранжирование. Два правых столбца с моделью отказа, которая для абляций не переобучалась, поэтому там оценка снизу. Полнота отказов во всех строках 1.0.

| вариант | top-1 | top-3 | top-1 voice | с отказом: top-1 | точность отказов |
|---|---|---|---|---|---|
| полный пайплайн | 0.9925 | 0.9975 | 0.9943 | 0.9925 | 0.9901 |
| без фонетического ключа | 0.98 | 0.995 | 0.98 | 0.95 | 0.8475 |
| без стемминга | 0.9925 | 0.9975 | 0.9943 | 0.9925 | 0.9901 |
| без починки склеек | 0.985 | 0.9925 | 0.9857 | 0.9725 | 0.9174 |
| без ключа, стемов и склеек | 0.97 | 0.99 | 0.9686 | 0.93 | 0.7937 |

Чего я не ожидал: фонетический ключ почти не нужен для ранжирования (минус 1.25 п.п.), зато нужен для уверенности. Без него у искажённых голосовых строк проседает совпадение улицы. Лучший кандидат часто остаётся верным, но модель отказа видит его на уровне негатива и отказывает. Отсюда точность отказов 0.85.

## Где ломается

**Дубли эталона.** Два из трёх промахов top-1: `a_0227` (Калужское 22-й км 10П) и `a_0414` (Магеллана 2). Оба верных id стоят в top-3. Детерминированно угадать выбор разметчика нельзя.

**Экзотический формат дома.** `a_0202`: «шоссе калужское 22-й км десять корпус омната 513», в эталоне дом «10комната 513». Парсер берёт 513 как номер, совпадения нет, отказ с P = 0.007. Это единственный ложный отказ и единственный промах top-3. Правило под одну строку писать не стал.

**Разметка покрывает 400 адресов из 1000.** Поэтому `scripts/selfcheck.py` подаёт каждый адрес эталона как запрос в трёх видах: как в эталоне с городом, без города, как в чате без типа улицы. Строки чистые, это проверка логики, а не устойчивости к шуму. Первый прогон нашёл четыре бага, невидимых на разметке: «Нижне-Печерская» и «Нижне-Волжская» распознавались как город, «квартал 110 1к2» разбирался как дом 110к1к2, «6-й» в эталоне и в запросе давал разные токены, а близнецы «Лескова 21» и «40 лет Победы 18» без города уверенно уходили в один из двух городов. После исправлений с городом и в чатовом виде 999 из 1000, исключение «10комната 513». Без города 995: ещё четыре отказа приходятся на близнецов, так и задумано. Метрики на разметке не изменились.

**Порядковые числительные словами не разбираются.** В разметке голос всегда отдаёт числа в названиях улиц цифрами: «9 мая», «2-я портовая», «60 лет». Количественные словами работают («сорок лет победы» станет «40»), порядковые нет: «шестой микрорайон три ка» получит отказ. Если в живом голосе они придут словами, это следующая правка в `numbers.py`.

**Без совпавшего дома решение отказывается всегда.** Проверил стресс-тестом: если у позитивов стереть распознанный дом или подменить его несуществующим номером, все 400 строк уходят в отказ, неверных ответов ноль. Даже на 216 строках, где на улице всего один дом. Модель выучила это из данных: среди негативов есть строки с идеально совпавшим названием улицы («шоссе ленинградское 52» при ул. Ленинградской в Иркутске, «луговвая 1» при проезде Луговом), и отличает их только дом. Следствие для отложенной выборки: непокрытый формат дома стоит переспроса, а не неверного адреса.

**Опасный негатив, которого в данных нет.** Одноимённая улица другого типа или из другого города, и номер дома случайно совпал с эталонным. Такую строку решение примет. Защищает только признак конфликта типа улицы, и то если тип назван.

**Запас по порогу.** Максимальная P среди негативов 0.34 («новгородская д3»), минимальная среди верных позитивов 0.88, если не считать «комнату 513». Между ними пусто, поэтому любой порог от 0.5 до 0.8 даёт одни и те же метрики. На отложенной выборке зазор, скорее всего, сузится.

**Оценка качества завышена.** Правила, словари паразитов и ручные веса я подбирал, глядя на все 500 строк. Кросс-валидация честна только для модели отказа, она переобучается в каждом фолде. Нулевой std у top-1 означает лишь, что ранжирование в фолдах не меняется. Независимая проверка есть только одна, и она слабая: строки `sample_input.jsonl` я видел при разборе данных, но предсказания по нему посмотрел в самом конце и правила после этого не менял. Там 10 отказов из 50, ровно столько негативов заявлено в условии: 4 реплики не про адрес и 6 адресов из Иванова, Сегежи, Чистополя, Владимира, Рыбинска и Череповца. У остальных 40 я вручную проверил, что выбранный адрес единственный правдоподобный в эталоне. Среди них три строки, где поле city указывает не на тот город: «розы люксембурк семь» при городе Волгоград ушла в Архангельск, потому что дом 7 на этой улице есть только там. Каждое правило разбора дома в `numbers.py` закрывало от одной до трёх строк, так что на новых 400 позитивах почти наверняка найдутся свои непокрытые форматы. Ожидаю top-1 на отложенной выборке на 1-2 п.п. ниже. Из-за поведения при сбое разбора дома эти потери уйдут в ложные отказы, то есть просядут top-1 и точность отказов, а неверных адресов почти не прибавится.

## Что дальше

**Разметка из основного пути.** Когда геокодер отвечает, у нас есть строка и координаты. Ближайший эталонный адрес в радиусе нескольких метров даёт метку для резервного матчера. Это реальные строки с настоящим шумом распознавания, без ручной разметки, и данные не покидают контур. На них я бы в первую очередь проверил разбор дома и откалибровал отказ.

**Частичный переспрос.** Сейчас отказ бинарный, хотя по признакам видно, что именно не сошлось. Самый частый сценарий сбоя это уверенная улица и несошедшийся дом, стресс-тест выше. Бот мог бы спросить только номер дома на названной улице. Для этого `match` должен возвращать причину отказа.

**n-best от распознавания.** Если ASR отдаёт несколько гипотез, матчер можно прогнать по каждой и взять лучшую по P. Пять гипотез это около 10 мс.

**Синтетический стресс-тест по всему эталону.** Сейчас проверено 400 позитивов на 1000 адресов. Прогон каждого адреса эталона через локальные TTS и ASR (например, Piper и faster-whisper) дал бы реалистичный голосовой шум на всех улицах, включая те, что в разметку не попали.

**Обучаемый ранжировщик.** Когда размеченных строк станет на порядок больше, заменить ручные веса градиентным бустингом с ранжирующей функцией потерь на тех же признаках. На 400 строках это переобучение.

**Дубли эталона.** Почистить справочник или отдавать группу id как один ответ.

## Как мерил время

Железо: контейнер с одним vCPU Intel Xeon @ 2.10 GHz и 4 ГБ RAM, Python 3.12.3, rapidfuzz 3.14.6, `cdist` вызывается с `workers=1`, всё считается в одном потоке. В замер попадает только вызов `Matcher.match` на одну строку: разбор, поиск улиц, признаки кандидатов, скор и решение об отказе. Время берётся `time.perf_counter()` вокруг каждого вызова, p50 и p95 считаются по всем строкам входного файла. За скобками остались импорт, чтение эталона и построение индекса (около 50 мс, один раз при старте), загрузка `model.json`, чтение входа, запись предсказаний и прогрев на первых 20 строках, которые потом меряются заново в основном проходе. Прогрев почти ничего не меняет: холодный первый вызов занимает около 3 мс. На 500 размеченных строках p50 от 1.7 до 2.0 мс и p95 от 2.6 до 3.1 мс в зависимости от запуска, p99 около 3.3 мс, максимум 4-5 мс. Три четверти времени уходит на `cdist` подотрезков фразы против 741 варианта названий, разбор строки занимает около 0.2 мс. От длины фразы задержка почти не зависит: 1.7 мс для строк до 4 слов и 1.9 мс для строк от 8 слов. До мягкого порога 200 мс запас примерно в 65 раз по p95.
